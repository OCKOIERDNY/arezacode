# Dependency Advisory Reachability — September 24, 2026

## Scope and counts

Snapshot from `bun audit --json` with Bun 1.3.14: **274 advisory/package records, 54 distinct package names**. The table below deduplicates within package by advisory ID and preserves each audit-reported affected-version range. Audit reports dependency versions, not application exploits.

Workspace/path classification is based on `bun pm why <package>` plus workspace manifests and source/config inspection. `runtime` means a dependency path exists from a runtime workspace; `build/dev` means its known path is through build, packaging, tests, or development. `optional` marks optional/peer paths, which may not be installed or loaded. `not in shipped entrypoints` means no relevant shipped entrypoint path was established in this trace; it does not prove absent from every possible deployment. Classes can overlap where workspaces have multiple paths.

## Advisory-specific reachability evidence

- **Local build artifacts checked (September 24, 2026):** `bun run build` succeeded in `packages/app`, `packages/web`, and `packages/enterprise` (`bun run build:cloudflare`). The app bundle `packages/app/dist/assets/index-CWL7Hekk.js` contains the DOMPurify sanitizer path. Astro's built Cloudflare worker `packages/web/dist/_worker.js/index.js` imports `astro@5.7.13` source modules. Enterprise output `packages/enterprise/.output/server/chunks/_/node.mjs` contains the Hono implementation, and its built route chunks instantiate Hono apps. These are local builds from the current workspace, not signed/released deployment artifacts.
- Built the OpenCode Node bundle with `MODELS_DEV_API_JSON=test/tool/fixtures/models-api.json bun run script/build-node.ts` from `packages/opencode` to avoid the build's remote model-catalog fetch. The resulting local `packages/opencode/dist/node/node.js` includes Arborist 9.4.0, pacote 21.5.0, tar 7.5.15, and provider-utils 4.0.23 and 4.0.50. The test catalog override changes model metadata only. This confirms those dependency versions and code are in the locally built Node artifact; it does not establish that a released Desktop/CLI artifact was built from this lockfile or which optional instances ship in every target.
- No configured build artifact was produced for `packages/function` or `packages/slack`; their reviewed entrypoints remain source/deployment-path evidence, not artifact confirmation. The desktop package build's prebuild downloads an external CLI in its default dev channel, so it was not run for this local artifact check.
- **DOMPurify:** `bun.lock` resolves `dompurify@3.3.1`, affected by inventory IDs 1115668, 1120802/1120803/1120813, 1117138–1117140, and 1124022–1124241/1138538 where their recorded ranges include 3.3.1. `packages/session-ui/src/components/markdown-cache.tsx` calls `DOMPurify.sanitize` after `parseMarkdown`; settings permit HTML/MathML and add SVG/path and selected attributes, forbid `style` and script/style contents, and enable named-property sanitization. The hook preserves `file:///` anchor hrefs, and adds noopener/noreferrer for `_blank`. App preloads `part.text` (`packages/app/src/pages/home/home-sessions-controller.tsx`) and Markdown rendering also sanitizes parsed block HTML (`packages/session-ui/src/components/markdown.tsx`). Thus untrusted session text is a plausible source of sanitizer input and the sanitized output is rendered; this establishes reachability of the sanitizer, not that any advisory's exact bypass payload/precondition succeeds. The package is in the app/session-ui browser bundle path; no advisory-specific exploit test was performed.
- **Hono:** `bun.lock` resolves Hono 4.10.7, below the listed fixed version 4.13.5 and within all listed Hono affected ranges whose upper bound exceeds 4.10.7; any narrower range must still be assessed against that precise resolved version. `packages/function/src/api.ts` registers public GET/POST routes, parses request query/JSON, and exports a Hono-backed worker; `packages/enterprise/src/routes/api/[...path].ts` validates JSON and path parameters in routes exposed through GET/POST/PUT/DELETE. Request bytes/URL are attacker-controlled at those boundaries, subject to route validation. This proves request-facing Hono routing is shipped in respective Cloudflare/enterprise service paths, not that every Hono advisory's method, encoding, malformed path, or body prerequisites are met. The separate `@hono/node-server@1.19.14` is below advisory 1139322's `<1.19.15` range; no direct import/callsite was established in those application handlers.
- **Astro / Cloudflare:** lockfile versions Astro 5.7.13 and adapter 12.6.3 fall in the respective inventory ranges (`astro` GHSA-1193723 `<7.2.8`; adapter GHSA-1107267 `<12.6.6` and GHSA-1117135 `<13.1.10`). `packages/web/package.json` makes both production dependencies; Astro config has `output: "server"` and Cloudflare adapter with `imageService: "passthrough"`. SSR routes/middleware and content pages exist, so deployed server code is a real artifact path. Passthrough configuration does not establish the image optimization endpoint behavior required by the adapter advisory; deployment-specific route and request preconditions were not verified. Astro advisory-specific vulnerable code paths likewise have not been matched to a concrete route/input in this inspection. The web package is a separate docs/web deployment, not evidence that Astro is bundled into desktop/CLI.
- **tar / pacote:** lockfile tar 7.5.15 is within all six listed tar ranges, including GHSA-1123940 (`<=7.5.18`) and 1145647 (`<=7.5.20`). pacote 21.5.0 falls in 1146559's `>=11.2.7 <21.5.1` range, and the root manifest applies `patches/pacote@21.5.0.patch`, modifying GitFetcher fallback behavior after tarball extraction fails. `packages/core/src/npm.ts` dynamically imports Arborist only inside `reify`; `Npm.add(pkg)` derives an npm package spec from its argument and passes it as `add`, while `Npm.install(dir, input)` builds specs from supplied name/version and only reifies for missing install state. Therefore a package spec / registry or git package archive can influence extraction on explicit package-add/install paths; normal HTTP request data is not directly passed here by the observed API. Core is a runtime dependency of CLI/server products and install APIs are exported; artifact inclusion is supported by the runtime dependency graph, but exploitability depends on the applicable archive and extraction-specific advisory conditions.
- **provider-utils:** root `packages/core/package.json` resolves 4.0.51, outside GHSA-1193659's `<4.0.33` upper bound, but `bun.lock` has nested 4.0.21/23/27/32 instances inside it and 4.0.33 at the fixed boundary. Core directly imports provider-utils in GitHub Copilot provider implementation (e.g. `src/github-copilot/copilot-provider.ts`, response input conversion, and response tools); its package manifest is runtime and Core feeds CLI/server/app compositions. Some nested versions belong to provider SDK packages, and optional gateway providers add non-uniform paths. The advisory concerns provider-utils HTTP request/response utility behavior; these imports establish package API use but this trace did not match the vulnerable helper to a selected Core call or establish attacker control of its relevant options/response fields. Mark vulnerable instances present and code path runtime-reachable, exploit preconditions unresolved; do not infer all instances ship merely from lockfile presence.
- **Axios:** `bun.lock` resolves Axios 1.16.1, inside all ten inventory ranges. It is introduced by Slack Bolt and web-api and is used through their SDK transport; `packages/slack/src/index.ts` starts a Socket Mode bot, accepts Slack message text, and submits it as OpenCode session prompt text. No direct Axios import in the application was found, nor evidence that this text controls URL, proxy, redirect, multipart, or other Axios transport configuration. The Slack package is a distinct service workspace and is not a desktop/CLI runtime dependency in its manifest; its Slack deployment does ship the dependency path. Whether each advisory's attacker-controlled option/request condition can arise in Slack SDK internals remains unestablished.
- **fast-xml-parser:** Dependency paths include document/config parsing; parser callsites and input provenance were not exhaustively matched to each advisory. Treat reachability as unresolved pending callsite/precondition review.
- **seroval:** SolidStart workspace dependencies include console/enterprise/stats apps, with optional framework/plugin paths. Loading in a shipped OpenCode desktop/CLI entrypoint is unconfirmed; server deployment and serialization callsites need separate review.

## Existing shipped-artifact and entrypoint check

This check combines local builds made September 24, 2026 with existing packaged outputs. `packages/app/dist`, `packages/web/dist`, `packages/enterprise/.output`, `packages/opencode/dist/node/node.js`, `packages/desktop/out`, and a macOS app under `packages/desktop/dist` are present. The App, Web, and Enterprise outputs were built from current workspace sources in this pass; the OpenCode Node output was rebuilt with the checked-in model test fixture to avoid a network fetch. Function and Slack deployment outputs were unavailable. Local build commands and dependency versions are recorded above; there is no signed/release manifest tying these outputs to a production deployment.

- **App renderer — DOMPurify:** App's configured entry is Vite build (`packages/app/package.json` `build: vite build`; `packages/app/vite.config.ts`), producing `packages/app/dist`. The newly built `packages/app/dist/assets/index-CWL7Hekk.js` contains the DOMPurify sanitizer path. Desktop's renderer entry uses the app Vite plugin and Electron Builder packages `out/**/*`; existing `packages/desktop/out/renderer/assets/main-BlDnJi7r.js` also has sanitizer identifiers, but that output was not rebuilt in this pass. The app's current local bundle and sanitizer callsite establish code inclusion; the old desktop bundle does not prove exact 3.3.1 identity.
- **Core/server and desktop main — provider-utils, tar/pacote:** The rebuilt `packages/opencode/dist/node/node.js` contains `tar@7.5.15`, `pacote@21.5.0`, Arborist 9.4.0, and provider-utils instances 4.0.23 and 4.0.50. The first provider-utils instance is within GHSA-1193659's `<4.0.33` range; 4.0.50 is outside it. Arborist and pacote code is bundled from the install path, and Core provider integrations load provider-utils helpers. This confirms vulnerable package code is present in this locally built Node artifact, but not that the matching release artifact uses it or that a specific advisory's attacker-controlled preconditions are met. Desktop's pre-existing main output was not rebuilt here.
- **Hono:** Enterprise's newly built route chunks instantiate Hono apps and `packages/enterprise/.output/server/chunks/_/node.mjs` contains the implementation. This confirms Hono code in the local Enterprise output; exact vulnerable instance in a released deployment and advisory-specific preconditions remain unconfirmed. Function source/config identify a request-facing Hono worker, but no configured build output or deployment manifest was available for `packages/function`.
- **Astro / Cloudflare:** The newly built `packages/web/dist/_worker.js/index.js` imports Astro 5.7.13 modules; the package manifest and lockfile select adapter 12.6.3. This confirms both package path and Astro code in the local worker output. The deployed worker revision was not available, and `imageService: "passthrough"` leaves adapter image-endpoint applicability unresolved.
- **Axios / Slack:** The Slack workspace depends on Bolt, whose lockfile dependency graph selects Axios 1.16.1, but there is no Slack deployment output/manifest locally. Existing OpenCode Node and desktop bundles have Axios text matches, which do not establish the Slack Bolt transport, package identity, or inclusion of that Axios copy. Slack-specific artifact reachability therefore remains unconfirmed locally.

**Limit:** these builds show local package inclusion and resolved dependency versions as built from the current workspace; they are not signed/released artifacts and do not establish deployed revision or exact advisory exploitability. Function and Slack artifact paths remain unconfirmed; desktop's default build would download an external CLI and was not run.

## Verification, limits, and interpretation

- Commands: `bun audit --json` and `bun pm why <package>` for all 54 reported names; inspection of package manifests and representative source/config paths.
- Advisory rows retain the registry's affected-version ranges, which can overlap, span multiple major lines, or not contain the exact workspace-resolved version. This report does not recalculate affected status per resolved instance. Nor does it map all duplicated/peer instances back to each advisory independently.
- The current advisory inventory is a point-in-time registry result; titles/severity and affected ranges are not proof of a reachable vulnerable code path. Runtime classification means dependency inclusion/path, not exploitability.
- Exploitability requires matching resolved version, shipped artifact and active code path, reachable attacker-controlled input, advisory-specific preconditions, and absence of effective configuration/mitigation. None of those conditions is established solely by `bun audit` or `bun pm why`.
- No dependencies or lockfiles were changed. No install/update was run. No credentials were queried or emitted.
